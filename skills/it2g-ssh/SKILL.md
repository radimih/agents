# SSH на хосты IT2G

Логин/пароль для хоста берутся из IPAM (`https://ipam.it2g.ru`), поэтому пароли
не нужно запрашивать у пользователя и не нужно их нигде сохранять.

## Что использовать

Всё через `scripts/it2g-ssh.sh` — он сам находит креды в IPAM, входит по SSH и
оборачивает команды в `sudo`. Команды ниже выполняются из каталога этого скилла
(`scripts/` лежит рядом с `SKILL.md`), поэтому `S=./scripts`:

```bash
S=./scripts

$S/it2g-ssh.sh 172.17.21.130 -- hostname                    # одна команда
$S/it2g-ssh.sh 172.17.21.130 -c 'systemctl status gitlab-runsvdir'  # то же -c
$S/it2g-ssh.sh 172.17.21.130                                # интерактивный shell
$S/it2g-ssh.sh 172.17.21.130 -f ./check.sh -- arg1          # скрипт на хосте
$S/it2g-ssh.sh 172.17.21.130 --creds                        # показать креды из IPAM
```

Отдельно, если нужны только данные из IPAM (без SSH):

```bash
$S/ipam-lookup.py 172.17.21.130           # JSON: hostname, user, password, root_*
$S/ipam-lookup.py 172.17.21.130 --refresh # игнорировать кэш
```

## Как устроен вход

1. `~/.config/it2g/domain.creds` (`username:password`) — доступ к web-интерфейсу IPAM.
2. IPAM ищется по IP: `page=tools&section=search`, затем страница адреса даёт поля
   `Логин`, `Пароль`, `Root_Login`, `Root_Password`.
3. SSH: порт `22`, пароль, host key не проверяется (`StrictHostKeyChecking=accept-new`,
   отдельный `~/.ssh/it2g_known_hosts`).
4. Порядок входа: `sadmin` с паролем из поля `Пароль` → при неудаче `root` с
   `Root_Password`. У `sadmin` на хостах `sudo` без пароля, поэтому команды и
   скрипты идут через `sudo -n`.
5. Результат IPAM кэшируется в `~/.cache/it2g-ssh/<ip>.json` (12 часов, режим 600).

## Правила

- Пароли из IPAM не выводить в чат, в файлы репозитория и в коммиты. Печатать их
  только если пользователь явно попросил (`--creds`).
- Ничего не менять на хосте без явного согласия: по умолчанию только чтение
  (логи, статусы, конфиги). Разрушительные операции (`rm`, `systemctl restart`,
  правка конфигов, `gitlab-ctl reconfigure`) — только после подтверждения.
- Скрипт для хоста писать локально во временный файл и запускать через `-f`;
  воспроизводить многострочные команды в `-c` не надо.
- Под `sadmin` уже root-права через sudo; второй `sudo` внутри скрипта не нужен.

## Типовой разбор логов

```bash
# что за хост и какая ОС
$S/it2g-ssh.sh 172.17.21.130 -c 'hostname -f; cat /etc/os-release | head -3'

# журнал systemd за последний час
$S/it2g-ssh.sh 172.17.21.130 -c 'journalctl --since "-1h" --no-pager | tail -n 100'

# ошибки в конкретном сервисе
$S/it2g-ssh.sh 172.17.21.130 -c 'journalctl -u <service> -p err --since "-24h" --no-pager | tail -n 100'

# GitLab Omnibus
$S/it2g-ssh.sh 172.17.21.130 -c 'gitlab-ctl status'
$S/it2g-ssh.sh 172.17.21.130 -c 'tail -n 200 /var/log/gitlab/gitlab-rails/production.log'

# свободное место / нагрузка
$S/it2g-ssh.sh 172.17.21.130 -c 'df -h; uptime; free -m'
```

Для больших файлов сначала смотреть `tail`/`grep`, а не читать лог целиком.

## Ограничения и подводные камни

- Поле `Пароль` принадлежит пользователю из поля `Логин`. Если там не `sadmin`
  (например `appsuser`), вход под `sadmin` не пройдёт — скрипт сам переключится на
  `root`. Об этом он пишет в stderr.
- TLS до IPAM проверяется, сертификат валидный (GlobalSign, `*.it2g.ru`). Если узел
  отдаёт неполную цепочку, `ipam-lookup.py` считает это ошибкой и завершается.
- REST API IPAM (`/api/`) недоступен без `app_id`, поэтому используется web-интерфейс.
- Нужен `sshpass`, сеть до `ipam.it2g.ru` и до хоста. Хост должен быть заведён в
  IPAM — иначе `ipam-lookup.py` завершится с кодом 2.
- Пароли в IPAM могут содержать `$`, `#`, `}`, `'` — не собирать команды вручную,
  использовать скрипты (`sshpass -e` передаёт пароль через окружение).
- Периодически пароль в IPAM меняется: при «Permission denied» по всем
  пользователям запустить `--refresh` и сверить поле в IPAM.
